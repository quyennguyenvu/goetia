# Goetia — engineering guardrails

Invariants distilled from the 2026-08-07 review + security audit. Keep these true; a change that breaks one is a regression even if tests pass. Full rationale: `docs/superpowers/specs/2026-08-07-hardening-and-remediation-design.md` and the two `docs/superpowers/plans/2026-08-07-*` plans.

Definition of done for any change: `corepack pnpm lint`, `corepack pnpm typecheck`, and `corepack pnpm test` all green; `corepack pnpm e2e` for main/preload/renderer wiring; and for packaging changes a real `package:mac` build that launches (see Packaging below).

## Product principle: chat ONLY

Goetia shows each service's chat surface and nothing else — no feeds, shops, menus, or other site functions (user decision, 2026-08-07):

- Recipes hide the host site's chrome (nav menus, headers, get-app/download CTAs) via recipe `css`, gated on the chat surface being mounted so login and captcha pages stay untouched (the shopee lesson; `display: none` keeps `textContent` readable for `count()`). Off-chat in-page links (profile/avatar CTAs, shared posts) may additionally be inerted with `pointer-events: none` (messenger, instagram), and chrome with no stable selector (hash-classed rails, role=button icons) is hidden per-tick via the recipe's `hideChrome` hook (instagram's nav rail) — still cosmetic; `chatPaths` remains the containment, and `hideChrome` must never return the chat surface or an ancestor of it.
- User-initiated reload returns the view to `SERVICES[].url` via `views.refresh` — **reload is the only way back** when a site's own links wander off chat, so don't weaken it. Reachable while a service page covers the window from `Go ▸ Reload Service` (⌘/Ctrl+R) and F5 (handled on both the shell and inside the view); the `service:reload` channel additionally backs the crashed-view placeholder, which needs a shell surface on screen. A user reload is dropped while the service is waking and inside `RELOAD_MIN_INTERVAL_MS` (`lib/reload-guard.ts`), so a spammed ⌘R or held F5 cannot keep restarting the load it is waiting on; the block is bounded because the wake self-expires at `WAKE_TIMEOUT_MS` and a crash ends the wake before the Retry placeholder renders. A history-back affordance was built and rejected instead (2026-08-13 — see `docs/superpowers/specs/2026-08-13-service-back-affordance-design.md`): back is browser chrome, and reload already lands on the chat URL. Crash auto-reload (`ResilienceManager`) keeps reloading the current URL via `views.reload`, which stays unguarded.
- Sites that are more than chat (facebook, tiktok) declare `chatPaths` on their recipe: once a document has been on a chat path, SPA routing off all of them makes the runner navigate back to the service URL (`SNAPBACK_MIN_INTERVAL_MS` floor; login flows never snap because they never reach a chat path). CSS hiding is cosmetic; `chatPaths` is the containment. A logged-**out** shell with no sign-in form in sight may declare `loginUrl` (2026-08-30, user decision; spec `docs/superpowers/specs/2026-08-30-logged-out-login-landing-design.md`): the runner lands there once per document and the site's own `redirect_url` brings the session back to `url`. TikTok and Shopee declare it (`tiktok-login.test.ts` pins the set) — TikTok's logged-out `/messages` is the feed nav plus an empty DM drawer; Shopee's logged-out `shopee.vn` dead-ends on the `/verify/traffic/error?…&is_logged_in=false` gate, so its `loginUrl` is **URL-based** (that gate only, which a signed-in user never lands on — no session marker needed) rather than DOM-based. Sites whose logged-out page already is a form (Slack) declare nothing, and every service still starts on `url` — the 2026-08-13 `firstRunUrl` teardown stands; nothing about first-run state is persisted.
- **An off-chat link opens in the OS browser, not in the view** (2026-09-04). A host rule cannot express this: a Messenger thread linking to `facebook.com/share/p/…` is the service's own origin, so `isNavigationAllowed` passes and the view just left chat — with the snap-back 30s away at best, and never at all for a cross-document load that never reached a chat path. So the service preload intercepts the click instead (`offChatLinkUrl`, capture phase + `stopPropagation`, so the site's router never sees it) and hands the URL to main on `service:openExternal` — a service channel validated on `serviceId`, re-checked with `isSafeExternalUrl` and throttled exactly like a scripted popup, which is why it grants no reach `window.open` did not already have. Three guards keep it from eating navigations the app needs: only services declaring `chatPaths` take part (on a chat-only site same-origin is still the app, and the service URL's path is no substitute — Discord's `/channels/@me` would make every other server's channel read as off-chat); it fires only while the document IS in chat, so no login, checkpoint or captcha page is ever taken out of the app; and a targeted anchor or a `download` is left alone, since `setWindowOpenHandler` already decides browser vs call popup vs sign-in popup. Trusted clicks only.
- New services land on the chat URL directly (`SERVICES[].url`), not the site's home page.
- Enabling and disabling services lives on Home (the welcome screen), reachable from the rail sigil and `⌘/Ctrl ⇧ G` (`⌘/Ctrl 0` is zoom's Actual Size). Settings never gets an enable toggle back: composition behind a modal is what let a service view bury the modal it was toggled from.
- **Home is a destination, not a toggle** (2026-08-25, user decision): the sigil and `⌘/Ctrl ⇧ G` always open it, and asking for Home from Home is a no-op — no settings write, no broadcast, no trip back to the last service. Leaving Home is a service tile, `⌘/Ctrl 1…9`, the quick switcher, or Escape (`Welcome`'s guarded handler, which never fires with nothing to go back to).
- **Goetia's chords win inside a page** (2026-08-28, user decision). A service page receives a key before the app menu and may swallow it (Discord bound the old ⌘⇧H), so every shell chord is declared once in `shared/shortcuts.ts` — the menu reads its accelerators from that table, Settings → Shortcuts renders its grouped list from it, and `lib/shortcuts.ts` matches it — and intercepted in each view's `before-input-event`, where `preventDefault` also drops the menu accelerator, so the interceptor runs the command through `commands.ts`, the same function the menu items call. Never add a menu accelerator without a table entry, or it silently dies in whichever service binds it. **Home is `⌘/Ctrl ⇧ G` and Pin Selection `⌘/Ctrl ⇧ S`** (2026-08-28, user decision): both are pressed with the right hand on the mouse, so both live on the left half of the keyboard — keep any new chord that pairs with a mouse action there too, and away from ⌘⇧Q/W/Z/X/C/V/T/R, which the OS and edit conventions own. Held keys repeat only zoom and reload (the reload guard rate-limits). Playwright cannot drive this path — CDP key injection reaches the renderer but bypasses `before-input-event` (verified 2026-08-28) — so `shortcuts.spec.ts` emits the event on the view's `webContents`. `View ▸ Toggle Developer Tools` opens a **detached** inspector (docked would shrink the host under the views' layout) for the service page on screen, or the shell when a surface covers it.
- **Purge and banish are orthogonal axes.** Banish clears the rail and keeps the login; purge (`src/main/purge.ts`) clears the login and never touches `disabled` or `order`. Home's `Purge all logins…` sweeps every service in `order`, summoned and unbound — it is the **only** path to an unbound service's credentials, since Settings → Services lists enabled services only, so narrowing the sweep to enabled services would silently strand them. Its confirm is an **in-app modal** (`PurgeConfirm`, z-40 above every other surface), not a native dialog: `showMessageBox` reports `checkboxChecked` only alongside the button press, so it can never disable the confirm until the sweep is acknowledged. Main is handed an already-confirmed decision and never poses the question — both channels stay shell-only, which is what keeps that safe. The completion count rides the `services:purgeAll` invoke return, never `ShellState`.
- Fresh installs start with every service disabled: the shell shows the welcome screen whenever all services are disabled (derived from settings — no flag). Zero enabled services must mean zero service views; see `resolveActivation` and the startup guard.
- Launch restores the surface you left: the last active service, or Home if that is where you quit (`resolveStartupSurface`, recorded by `rememberSurface` on every change). A recorded service that is now disabled or gone opens Home rather than silently substituting another.
- **Pins are the user's todo list, on Home** (2026-08-26; spec `docs/superpowers/specs/2026-08-25-pinned-messages-design.md`). Captured main-side from the page context menu (`pin-message` in `lib/context-menu.ts` → `ViewHooks.onPinMessage`) — no service-side IPC. `PinStore` (`src/main/pins.ts`) persists to `pins.json`: the one exception to "conversation content never touches disk" — explicitly pinned text lives there and leaves with the pin; the activity log stays in-memory. Pins survive purge and banish (a banished pin dims; its open is `show-only`). Acknowledgement is the tally pill beside the Home sigil (count + pulse) — never a badge on the sigil (a corner count circle is the unread language) and never a shell toast at pin time, because the service page covers the shell; at `PIN_CAP` the menu item renders disabled. Pin 0 is "in progress" by position alone; the board is one `Reorder.Group` with a drag-local draft and ONE `pins:reorder` per drop; Done/unpin toast with Undo (`pins:restore`) only on Home. `pins:open` reuses `resolveBannerClick` verbatim — hrefs never leave main. Capture has two doors — the context menu and `Edit ▸ Pin Selection` (⌘/Ctrl ⇧ S → `views.pinSelection`, which reads the selection with `executeJavaScript`): sites that own right-click (Discord draws its own menu on messages; Shift+right-click also reaches ours) need the second. The store dedupes on service + href + text. The conversation label is best-effort from `document.title` (`conversationFromTitle`) — main never learns per-service DOM, so an author or a reliable thread name would need per-service recipe hooks. Opening routes in-page by **resolved** URL and is a no-op when the document is already there (`conversation-open.ts`): a pin must never reload the SPA it was pinned in. Sites whose URL names no thread (WhatsApp) declare recipe hooks `conversation(doc)` / `openConversation(doc, name)`: the name is read at pin time through the frozen `window.__goetia.conversation()` the preload installs, rides the pin, and is tried **before** any URL logic on open. WhatsApp's header names the chat in a `span` with **no** `title` attribute — the header's only `span[title]` is the member list (the 2026-08-28 bug); rows are `role=row`, the name is the `span[title]` in `cell-frame-title`, and the message preview beneath is a `span[title]` too, so never match on `#pane-side span[title]` alone (`tests/fixtures/whatsapp-chat.html` is the oracle). Meta sites title themselves only "Messenger", so messenger names the thread from the sidebar row whose link is the document URL (`conversationFromRows`); instagram's rows are `role=button` with **no href** (live 2026-08-29), so it names the `aria-pressed` row and opens by clicking the row whose name matches — never key Instagram on `a[href*='/direct/t/']`, the only such link is the rail's Messages link, which repoints at a thread while it is unread. TikTok likewise names the open chat from `dm-new-chat-nickname` and clicks the `dm-new-conversation-nickname` row; its chrome hides only under a session (`top-dm-icon`), because the logged-out page mounts the empty DM drawer too. Zalo names the open conversation from `.threadChat__title .header-title` and its rows are `.msg-item` / `.conv-item-title__name` in a virtualized list (NBSP-joined — flatten before comparing); because Zalo ignores synthetic clicks, `openConversation` may return a **point** rather than `true`, which the preload sends on `service:trusted-click` (the keep-alive channel, renamed; still a service channel validated on `serviceId`) for main's `sendInputEvent` — a row still outside the list after `scrollIntoView` is refused, since its centre would hit a neighbour. `tests/fixtures/zalo-chat.html` is the oracle.

## Notifications & mute

- **One sound per message.** Most services ding in-page themselves, so Goetia sounds only banners the page could not have made: `notification:fired` carries `synthetic` (true only from a recipe's `synthNotification`, where the site delegates to push Electron can't receive), and `soundOptions` is the single place that decides. Setting `sound` without `silent` is a bug — macOS reads the name, Windows/Linux read the flag.
- **Mute means silence, never blindness.** Muting suppresses the banner _and_ the page's own audio (`views.applyAudioMute`, `audioMuted` = the inverse of `shouldNotify`), and leaves badges alone. `aggregateBadges` must stay ignorant of mute — the badge is how a muted service is still found.
- **Quiet hours are a scheduled global mute.** Effective silence is `globalMuted || quietNow`, decided solely by the `shouldNotify`/`audioMuted` pair in `lib/notification-rules.ts` — never gate a banner or page audio anywhere else. Engagement is computed from the wall clock (`lib/quiet-hours-rules.ts`), never persisted; boundary fires and `setGlobalMuted` share one side-effects tail in `index.ts`; unmuting mid-window records `quietOverrideWindowStart` and holds until the next window; `aggregateBadges` stays ignorant of quiet hours too.
- **Banner click lands in the conversation.** `resolveBannerClick` (`lib/notification-click.ts`) is the single decision for banners, ⌘K rows and pins: a `href` is validated against the service origin plus the `chatPaths` prefixes (mirrored on `ServiceMeta`, sync-enforced by `recipes.test.ts`) — and for a recipe with **no** `chatPaths` same origin is the whole check, because a chat-only site is all chat and its service URL's path was never a boundary (Discord's is `/channels/@me`; every server-channel pin at `/channels/<guild>/<channel>` failed that prefix and silently did nothing, 2026-09-04). A **dead** view can only be handed the URL as its wake load (a cross-document `loadURL`). A **live** view gets **every lane in one `OpenRequest`** — the shim `clickId`, the conversation name, the href/URL — and `openConversationInPage` runs them in order, replay → recipe row click → same-URL → anchor click → full load, moving on only when a lane **reports a miss**. Main used to pick one lane blind, and a replay whose banner the site had already closed did nothing at all. The request travels by `webContents.postMessage` with a `MessageChannelMain` port the preload answers on (`{ lane, url }`, parsed by `parseOpenReply`, bounded by `OPEN_REPLY_TIMEOUT_MS`) — no new IPC channel, only main can mint the port. A miss logs `[open] <service> miss: lanes=…`, the evidence for the next round. Main never learns per-service conversation DOM. Peek views live `BANNER_GRACE_MS` past their last banner so the replay target survives a prompt click; every failure falls back to plain activation.
- **The waking cover is for loads main asked for, and nothing else.** Every `loadURL`/`reload` main issues on a service view goes through `views.load`, which marks the view in `MainLoads` (`lib/main-loads.ts`); the next main-frame cross-document `did-start-navigation` claims the mark and only then does `onNavigate` run `waking.begin`. A navigation the page made on its own runs over a live document and is never covered: the in-page route's fallback load (Messenger's chat list is virtualized — a real signed-in DOM carries anchors for only ~19 threads — so a pin or ⌘K row for any other thread finds none and `openConversationInPage` ends in `assign(url)`, a full SPA reboot), and equally a site's own full-page thread switch or login redirect. The first cut exempted only the fallback load by a timed stamp, and Messenger still raised the cover after a far pin when the next thread click reloaded the document on the site's initiative (2026-09-05). `forgetReplay` still runs on every cross-document navigation — the document really is being replaced. A dead view's `views.openConversation` (`loadURL`) is a genuine wake and still covers.
- Every global-mute path (bell, tray, app menu, `⌘/Ctrl+⇧+M`) goes through `ctx.setGlobalMuted`, which persists, re-mutes the views and rebuilds both menus — their checkmarks are baked in at build time. Don't call `settings.update({ globalMuted })` directly.
- The accelerator is declared in the app menu only; the tray's copy of the item carries none, or one keypress fires the toggle twice.
- **Recents are the banner stream remembered.** The activity log (`lib/activity-log.ts`) is bounded and in-memory only — conversation titles never touch disk (pins are the sole, explicit exception — see Product principle); it is fed by throttled `notification:fired` events including silenced ones. The switcher fetches once per open (`activity:recent`, invoke) — never a per-banner broadcast — and `activity:open` carries an opaque id: hrefs stay in main and re-validate through `resolveBannerClick` at click time.
- **A recents row opens through the same lanes as its banner**, in one decision (`resolveBannerClick`, which also serves pins): a validated `href` (a synthetic banner's own, or one the row **learned** — see below; a shim banner's href field is page-controlled and never a lane by itself, `openHref` in `lib/activity-log.ts`), the shim's `clickId` — the site's own onclick, precise because it knows the thread id — and the conversation's **name**. The name lane exists because most services ding themselves, so their banners come through the shim with no href at all: before it, every Discord and WhatsApp recents row silently degraded to plain activation (2026-09-03). Three rules keep the shim lane honest. `ActivityLog.forgetReplay(id)` runs on `ViewHooks.onNavigate` because the shim's registry dies with the document and its ids restart at 1 — a kept id would replay a _different_ banner, which is a wrong thread, not a missing one. The registry **keeps a banner the site closed** (`close()` is a no-op there): sites close banners on a timer or when the thread is read elsewhere, and the onclick still leads to that thread. And `REGISTRY_CAP >= ACTIVITY_CAP` (asserted in `notification-shim.test.ts`) — a 20-deep registry under a 50-row list left every older row dead on arrival (2026-09-04). **A landed replay teaches the row its URL**: when the replay lane moved the document (main compares `getURL()` before and after, and the page's report must match), `ActivityLog.learnUrl` stamps `landedUrl` on every entry of that conversation and `append` inherits it, so the row keeps a durable lane once the handle is gone — the only way a Discord row survives a reload, since Discord has no name opener. The name lane carries **no URL**: it is set only for `ServiceMeta.bannerTitleNamesConversation` services (whatsapp, zalo — `recipes.test.ts` pins the set and requires `openConversation`), where the banner title _is_ the thread name and no URL can single a thread out, so a name matching no row must leave the page where it is rather than reload the chat list. WhatsApp's chat list is **virtualized** — only the rows in view exist — so `openWhatsAppConversation` is async: it walks the pane from the top a page at a time (`SCROLL_SETTLE_MS` per page, `SCROLL_MAX_PAGES` cap, scroll restored on a miss); a `Recipe.openConversation` may return a promise for this reason, and must stay bounded.
- **A ⌘K row leads with the conversation, not the sender.** Discord packs both into one banner title — `Author (#channel, Server)` — and its author half is not always a name (an unresolvable member arrives as the literal `Username`, reported 2026-09-03), so `splitBannerTitle` (`lib/banner-title.ts`) parses it once on the way in: the channel becomes the row's primary text and the dedupe key, the sender trails it dimmed and stays searchable. Discord's trailing field is **dropped** deliberately — it is the server on one banner and the category on the next for the very same channel, so keeping it split one channel across two rows. Every other service titles its banners with the conversation already and passes through untouched; never guess a split that is not there.

## Process boundaries (never weaken)

- Shell window: `contextIsolation: true` + `sandbox: true`. Never turn off.
- Service views: `contextIsolation: false` + `sandbox: false` — required by the recipe workarounds. Harden _around_ this (see Security); never rely on it for isolation, and never add `nodeIntegration: true`.
- `src/shared/**` stays process-agnostic: no `electron` and no DOM imports, so it is safe to bundle into both main and the sandboxed preload.
- Pure decision logic goes in a `lib/` helper with a vitest unit test; keep `views.ts` / `index.ts` / `ipc-handlers.ts` as thin wiring.
- Service views are layered above the shell renderer, so a visible view covers any shell surface. No code path may make a view visible while `anyOverlayOpen()` is true (settings, quick switcher, home) — resolve activation with `views.activate(id, { show: false })` and let `showActive()` present it when the surface closes. Startup is a code path too: a restored-open Home must activate its view hidden. Every surface toggle routes through `setOverlayOpen` / `setHomeOpen` (`activate.ts`), whose shared `presentSurface` re-reads `anyOverlayOpen` instead of pairing its own hide/show: a handler that showed the view whenever _its_ surface closed raised the last service over an open Home (2026-08-25).

## Security (every new service, IPC channel, or view must hold these)

- **Electron fuses** in `electron-builder.yml` stay set: `runAsNode`, `enableNodeOptionsEnvironmentVariable`, `enableNodeCliInspectArguments` off; `enableCookieEncryption`, `enableEmbeddedAsarIntegrityValidation`, `onlyLoadAppFromAsar` on; `resetAdHocDarwinSignature: true`. Valid keys are schema-checked — `enableRunAsNode` is NOT one; a bad key fails the whole config with "electronFuses should be one of these: null".
- **Entitlements**: `build/entitlements.mac.plist` grants only `allow-jit`, `allow-unsigned-executable-memory`, `disable-library-validation`, and the call-media pair `device.audio-input` + `device.camera` (2026-08-16 — calls are chat; the matching usage descriptions live in `electron-builder.yml` `extendInfo`). Never add `allow-dyld-environment-variables` — it reopens the injection path the fuses close.
- **IPC**: every channel is registered through the `register()` wrapper in `ipc-handlers.ts`, which enforces `ipcSenderAllowed`. A new channel MUST be classified: shell-only → add to `SHELL_ONLY_CHANNELS` in `shared/ipc.ts` (only the shell frame may send it); service channel → carry a `serviceId` field so it is validated against the sending frame. Never act on an attacker-controllable payload (persist settings, spawn, navigate) without that check.
- **External links**: only ever `shell.openExternal(url)` when `isSafeExternalUrl(url)` is true (web schemes only). Two exceptions to deny-by-default `window.open`. The first is a call: a URL passing `isCallPopup` — or an `about:blank` popup from a call-declaring service (`isBlankCallPopup`) — opens as a **hidden inert guest** that keeps the page's scriptable same-process handle (Chrome parity; Messenger writes into and navigates the popup it opened) but **never commits a navigation**: an in-process guest navigation crashes the shared renderer while the opener's Node env has pending work (electron#36858 class, reproduced 2026-08-16), and `about:blank` guests ignore webPreferences overrides so they can't be hardened. Instead a guest navigation to an `isCallPopup` URL is adopted into a standalone hardened call window (`contextIsolation` + `sandbox` on, no preload, no opener, same `persist:<id>` partition) whose own navigations must pass `isCallPopup` or `isNavigationAllowed` or it closes; any other guest navigation closes the guest. Popups-from-popups stay denied, guests die with their opener view, call windows close on service destroy (never on service switch — a call outlives the surface), and the service preload bails on `window.opener`. The second exception is a sign-in dialog: a URL passing `isIdentityPopup` (`lib/identity-policy.ts`, a **global** provider table — user decision 2026-08-31; spec `docs/superpowers/specs/2026-08-31-social-login-design.md`) opens as a **visible hardened popup** (isolated, sandboxed, same `persist:<id>`) that keeps `window.opener`, because the callback page finishes through `postMessage`; it may roam any provider host (`isIdentityHost`) or an `isNavigationAllowed` host, main frame only, and anything else closes it. Never adopt it into a fresh window (that severs the opener) and never add a provider host to `ALLOWED_HOSTS`. Refused scripted popups (`disposition === 'new-window'`) log `[nav] popup denied:` — the evidence for growing the table. Identity popups close with the service and on purge (`closeIdentityWindows`). The contained window hands a login back on `will-redirect` **before** the callback commits, and only there: `will-navigate` may carry a POST body Electron does not expose (Apple's `form_post`).
- **Shared Facebook identity** (2026-09-01, user decision; spec `docs/superpowers/specs/2026-09-01-shared-facebook-identity-design.md`). A "Continue with Facebook" popup borrows `persist:messenger`'s facebook.com cookies for the popup's lifetime only — Messenger's URL _is_ `www.facebook.com/messages/`, so its partition is the Facebook session by construction. Six rules gate it (`lib/identity-share.ts` `shouldSeed`), and the one that carries the security is **`FB_APP_IDS`**: without a per-service app id captured from a live sign-in, nothing is ever seeded. That table is what stops a malicious or XSS'd service page from opening its _own_ `dialog/oauth` against a signed-in jar and collecting a token on one click — the popup guard cannot contain that, because the SDK answers by `postMessage` through the `staticxx.facebook.com` arbiter and never navigates anywhere refusable. Never fill an entry in from memory. `FB_APP_IDS` refuses a stranger's app, **not the site's own app turned against the user** (an XSS'd shopee.vn opening Shopee's real `client_id` passes it), so seeding additionally asks **Touch ID, else a native confirm** (`identitySharePrompt`) every time — not a passkey and not WebAuthn, just the passkey prompt's local verification reused before a credential crosses partitions, and asked only after rules 5 and 6 so a popup that would not be seeded never prompts. `unseed` **verifies** before it unmarks: `cookies.remove` reports a url matching nothing by doing nothing, so unmarking on faith would strand a live session AND hide it from the boot sweep. The seed is taken back `IDENTITY_SEED_GRACE_MS` (10s) after the popup closes, and `identity-seeds.json` (service ids, never a cookie value) lets the next boot clean up after a crash. Rule 6 — target jar must have no Facebook session — is what leaves Instagram's own Log-in-with-Facebook cookies alone. Timing: `setWindowOpenHandler` is sync and every cookie API is async, so `seedIdentityPopup` stops the popup's load, seeds, and replays it with `httpReferrer`; the sync gate (`maySeed`) must decide **before** the first `await`, because a stopped popup is blank until something re-navigates it.
- **Permissions**: grant only via `permissionAllowed` (origin-checked; grants just `notifications` + `media`). Don't broaden the allowlist or drop the origin check.
- **Passkeys are a software authenticator in main** (2026-08-30, user decision; spec `docs/superpowers/specs/2026-08-30-goetia-passkeys-design.md`). The service preload's `webauthn-shim.ts` only asks; `PasskeyAuthenticator` validates the rpId against the origin main reads from `e.senderFrame.url` — never the payload — verifies the user (Touch ID, else a native confirm; `UV` is set on an accepted confirm, as 1Password/Bitwarden do), and signs. Private keys live `safeStorage`-encrypted in `passkeys.json`, one store keyed by rpId across services (safe because rpId is bound to the frame origin, not the partition), and **survive purge and banish** — removal is Settings → Passkeys. `webauthn:create`/`webauthn:get` are service invoke channels validated on `serviceId`; `passkeys:*` are shell-only. One ceremony in flight per view, `WEBAUTHN_TIMEOUT_MS` cap, sign counter 0, `BE = BS = 0`, attestation `none`. No CDP virtual authenticator (an attached debugger disables background throttling). The contained and call windows have no preload and keep raw Chromium behaviour.
- **Navigation containment**: `isNavigationAllowed` / `ALLOWED_HOSTS` in `navigation-policy.ts`, **enforced** on `will-navigate` and `will-redirect` in `views.ts` (2026-08-22), **top-level frame only** via `shouldContainNavigation` — `will-redirect` also reports a subframe's 302, and containing one cancelled Microsoft's passkey iframe and opened it as a blank window (2026-08-29); a login page's third-party iframes are not the view's origin. A service view may never carry an unlisted origin — it runs unsandboxed with the recipe preload, which is the whole reason the guard exists. An `ALLOWED_HOSTS` entry starting with `.` is a suffix (`.slack.com` matches `slack.com` and any subdomain, never `evilslack.com`) — the only way to express per-workspace hosts. The list is knowingly incomplete: tenant SSO and ADFS hosts are per-organization arbitrary domains, so a **refused navigation is contained, not dropped** — it opens in a hardened window (`openContainedWindow`: isolated, sandboxed, no preload, same `persist:<id>`, one per service, replaced not stacked) which hands the URL back to the service view the moment it lands on an allowed host, and dies with the service. That fallback is what makes enforcing safe without a completed live-login pass; don't remove it and leave enforcement on. Every refusal is still recorded by `NavigationAudit` (deduped per service+origin, capped) — `[nav] contained:` lines are the evidence for widening `ALLOWED_HOSTS`. `GOETIA_NAV_ENFORCE=off` exists only to confirm a suspected false block.
- **Notifications** flow through `NotificationRouter`, which is rate-limited per service (`NotificationThrottle`). Don't add a second, unthrottled path.
- **Renderer CSP**: `index.html` and `loading.html` keep `default-src 'self'` plus `object-src 'none'; base-uri 'self'; frame-src 'none'`. No remote scripts/styles/fonts, no `innerHTML`/`dangerouslySetInnerHTML` in the shell.

## Reliability & performance (recipes run forever, even hidden)

Recipe polling runs at the full `intervalMs` (~2s) even while a view is hidden (websockets exempt the page from Chromium throttling). So cost matters 24/7.

- `count(doc)` must be cheap and must always settle: no `getComputedStyle` / `getBoundingClientRect` sweeps over large lists (scope selectors, prefer aria/attribute signals); no `getAll()` over a whole IndexedDB store per tick. A `count()` that hangs is abandoned by the runner's `COUNT_TIMEOUT_MS` race — don't rely on that, but never return a promise that can never resolve/reject.
- Report on change only: the runner de-dups counts and only reports `stale` on the transition into stale; `MainState.setRuntime` skips the broadcast on a no-op patch. Don't reintroduce per-tick broadcasts.
- Tile reorder never streams to IPC: `Reorder.Group` fires `onReorder` on every crossing, so a crossing must only ever touch renderer state — wired straight to IPC, one drag would be one settings write, one broadcast and one app-menu rebuild per crossing. The rail uses `useTileReorder` (drag-local draft, one `service:reorder` on `onDragEnd`; the draft clears when the broadcast lands, not on commit, so the drop never snaps back for a frame). Home's board goes further: the whole edit is staged — clicks move tiles between sections, drags reorder `staged` locally — and ONE `settings:update` (disabled + order together) lands on confirm, so adds, banishes and reorders commit as a single frame (2026-08-15, user decision). While Home is open a rail drop also lands on the board: a clean board follows the new live order silently (`followLiveOrder`), a dirty one holds the drop behind `RailReorderPrompt` — discard the staged edit and reorder, or keep editing (the rail snaps back and `home:setOpen` returns the board) — so reorder still reaches IPC at most once per drag (2026-08-24, user decision).
- Bounded timers: any `setInterval`/`setTimeout` or `webContents`/`session` listener you add must be cleared on `destroy()` and on quit. Guard deferred callbacks with `!view.webContents.isDestroyed()`. `startReadyPoll` is capped at `READY_POLL_MAX_ATTEMPTS`; keep new polls bounded too.
- Light Sleep peeks recreate a sleeping service's view hidden (`views.ensure`, never `activate`/show), one service at a time, and destroy it on the first `unread:*` report (`ctx.noteUnreadReport`) or `PEEK_TIMEOUT_MS`. The hibernate step of the sweep skips the in-flight peek; peek teardown stamps `lastPeekEndedAt` and sets `hibernated`. Mute and quiet hours never pause peeks — badges keep counting. The sweep hands off to the next peek through `PEEK_STAGGER_MS` rather than chaining, so a boot where every service is due is not a queue of back-to-back cold loads. `peekSaver` (off by default, Settings) is the only thing allowed to stretch the interval: `peekInterval` doubles it per peek that reported nothing new, caps at `PEEK_BACKOFF_MAX`, and starts at the cap on battery; any change in the count or `noteActivated` resets the streak. Off means exactly the old cadence — badge staleness is a user-visible cost, so it stays opt-in.
- Auto-banish is the hibernation sweep, one step later: opt-in (`autoBanish`), decided by `shouldBanish` (`lib/banish-rules.ts`) off the persisted `lastUsedAt` — stamped only by activation (`rememberSurface`), never by banners, badges, or peeks; unstamped clocks seed at the first enabled sweep. All due services land in ONE `ctx.banishServices` patch through the shared `applyDisabledChange` tail, and a sweep that banished skips peek scheduling (its settings snapshot is stale). **Summoning restarts the clock** (`stampSummoned`, folded into the same `settings:update` write so Home still commits as one frame): the sweep's own seeding only covers a service that was NEVER activated, so a service used days ago and since banished was due the instant it came back to the rail — summoning all ten re-banished three of them within one 60s sweep (2026-09-03).
- **`keepRendered` is two mechanisms, not one** (Zalo): the preload's `installVisibilitySpoof` pins `document.visibilityState`/`hidden` at the JS level, and `setBackgroundThrottling(false)` additionally exempts the renderer's timers from Chromium throttling. Only the first is what Zalo's unmount-when-hidden behaviour needs; the second is the 24/7 cost. `GOETIA_KEEP_RENDERED=throttled` keeps the spoof and drops the exemption — the open experiment (R7). Do not flip the default on reasoning alone: the failure it guards against (Zalo's "Kích hoạt" modal, frozen badges, keep-alive clicks needing real `getBoundingClientRect` coordinates) only shows up in a live logged-in session left idle. Note that background throttling cannot be measured under Playwright or any attached debugger — Chromium disables throttling whenever one is attached, so a driven run shows an unthrottled renderer either way (verified 2026-08-22).
- `ResilienceManager` forgets a service's crash count only after a `DWELL_MS` uptime — don't reset it on every `did-finish-load`, or the auto-reload cap stops working.
- Window resize is coalesced via `scheduleLayout()`; don't add per-event heavy work in the `resize` handler.
- Window lifecycle: the app assumes one long-lived window. With close-to-tray off the window is destroyed and the app quits; keep `broadcast()` and tray handlers guarded by `win.isDestroyed()`.

## Adding a service (do all of these)

1. Add the id to `ServiceId` and an entry to `SERVICES` (`shared/services.ts`); add it to every record in `DEFAULT_SETTINGS` (`order`, `muted`, `disabled`, `neverHibernate`, `zoom`, `lastUsedAt`) in `shared/types.ts`.
2. Write `src/preload/recipes/<id>.ts` honoring the cost rules above. Keep `ServiceMeta.waitForReady` in sync with whether the recipe defines `ready()` (`recipes.test.ts` enforces this).
3. Add a fixture in `tests/fixtures/` and a row in `recipes.test.ts` — the fixture is the oracle for the unread count; `count()` must return `{ direct: 0, indirect: 0 }` on `blank.html` and never throw.
4. Add the service's hosts (incl. auth-redirect hosts) to `ALLOWED_HOSTS` in `navigation-policy.ts` — `.example.com` for a suffix match. Then run a live login and check the log: any `[nav] contained:` line is a host the flow needs, and until it is listed that login detours through the contained window. Declare its call popups and sibling call origins in `lib/call-policy.ts` (empty lists if it has no calls). Never list a host under a shared public suffix (`*.github.io`, `*.co.uk`) without first adding a public-suffix check to `rpIdAllowed` — the passkey rpId rule assumes no allowed host does.
5. Add notification icons under `resources/notification-icons/`.
6. Don't grant it extra permissions or a new unvalidated IPC channel.

## Packaging

`corepack pnpm package:mac` produces an ad-hoc-signed DMG. Verify a real build launches and the fuses stuck: read them from the packaged app via `@electron/fuses` `getCurrentFuseWire` (byte `49`='1'/on, `48`='0'/off) — the CLI is not on PATH; require the module from `node_modules/.pnpm/node_modules/@electron/fuses`. `package:win` needs a Windows machine. Both apps are unsigned/ad-hoc: a _downloaded_ copy is gated. The ad-hoc signature is valid (`codesign --verify --deep --strict` passes) — what Gatekeeper rejects is the missing notarization ticket, so on macOS 15+ the dialog is "Apple could not verify … free of malware" (**not** "damaged", which means a _broken_ signature — a different bug) and its default button is Move to Trash. Right-click → Open was removed in macOS 15; the two working escapes are System Settings → Privacy & Security → Open Anyway, or `xattr -dr com.apple.quarantine`. Windows SmartScreen → Run anyway. Only paid signing + notarization removes the gate; locally built copies aren't quarantined. User-facing steps live in the README and `.github/release-body.md` (which is prepended to every release's notes — keep the two in sync). Ad-hoc signing also means each build's designated requirement is its own cdhash, so every rebuild re-prompts for the `Goetia Safe Storage` keychain item that `enableCookieEncryption` creates — expected, answer Always Allow, and never turn the fuse off to silence it. Fix + costs: `docs/superpowers/plans/2026-08-07-code-signing-and-notarization.md`.
