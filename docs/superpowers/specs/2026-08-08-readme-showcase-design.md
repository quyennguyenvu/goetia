# README showcase design

**Date:** 2026-08-08

**Goal:** Turn the README from an install walkthrough into a showcase — a banner, real screenshots of the app, and a short argument for why Goetia exists — without putting any of the author's private conversations into a public repo, and without weakening the README's job as the one page a non-technical user needs.

## Context

- The README today is ~230 lines: a two-sentence intro, then ~130 lines of Gatekeeper/SmartScreen install prose, then build/packaging/notes. No images anywhere in the repo except icons (`resources/`) and the seven maskable service logos (`src/renderer/src/assets/logos/`).
- Prose wraps at 80 (`.markdownlint-cli2.jsonc`, `MD013`), tables and fenced code exempt. `"default": true` means **MD033 forbids all inline HTML** — which rules out a centered banner, `<picture>` for theme-aware images, and `<details>` folding.
- The e2e harness already supports everything a capture script needs:
  - `--goetia-user-data=<dir>` points the profile at a throwaway directory (`tests/e2e/welcome.spec.ts`).
  - A `settings.json` seeded in that directory controls `disabled`, `theme`, `railPosition`, `muted`, and `order` — `SettingsStore` is a plain `Conf` with `configName: 'settings'` over that `cwd` (`src/main/settings.ts`, `tests/e2e/smoke.spec.ts`).
  - `--goetia-e2e` injects a fake unread count of `3`, so a badge screenshot exercises the real recipe→runner→badge path rather than a mockup.
  - Stable `data-testid` locators exist on every shell surface — `welcome`, `rail`, `switcher`, `settings`, `update-toast` — so a capture script waits on the same selectors the specs do.
- `.gitignore` has no image or `docs/` rule, so a new `docs/media/` commits without changes.
- CLAUDE.md requires the README's user-facing install steps and `.github/release-body.md` to stay in sync.

## Decision: screenshots show only Goetia's own chrome

A fresh profile means every service is logged out. Enabling one to fill the content pane loads the live site, so the frame would carry WhatsApp's or Telegram's own login UI — third-party interface shipped in this repo, and a reader sees a login wall and concludes the app is broken.

So every committed screenshot frames Goetia's own surfaces only: the welcome picker, the rail, the quick switcher, settings, the loading overlay.

Consequences, accepted:

- No hero image of real conversations. The showcase argues the differentiators in prose and uses screenshots to prove the app is finished, not to prove people chat in it.
- In exchange the captures contain zero private data, can be regenerated by anyone who clones the repo, and raise no question about reusing another company's UI.
- A sanitized real-chats hero can be dropped in later without reworking anything; it is simply not part of this change.

Rejected alternative: screenshotting the author's live profile and blurring names. It produces the most persuasive image, but the result is unregenerable, one careless crop leaks a contact, and a blurred screenshot reads as evasive.

## Decision: claims first, screenshots as proof

Goetia's real edge is a claim no screenshot can make — *it shows the chat surface and nothing else*. A screenshot of a chat list looks like every other multi-service client's screenshot. So the README leads with six selling points, then runs a visual tour underneath them.

Rejected alternatives: a screenshot-led product tour (buries the differentiators in captions), and a problem→solution opening (spends the top of the page before showing anything).

## Assets: `docs/media/`

### Banner

`banner.svg`, hand-authored, composing the existing Ember Portal mark (`resources/icon.svg`) with the wordmark and the seven service glyphs. Theme handling lives inside the SVG via a `prefers-color-scheme` block, so one file serves light and dark and the README needs no `<picture>` for it.

### Captures

Five surfaces × light and dark = 10 PNGs, each cropped to the window, ~1400px logical width, with a combined budget under 1.5 MB. If the set exceeds that, drop the `waking` pair first.

| File stem | Surface | Seeded state | What it proves |
| --- | --- | --- | --- |
| `welcome` | Welcome picker | fresh profile (all disabled) | Seven services in Goetia's own visual language — the lead image |
| `rail-badges` | Top rail | two enabled, one muted, `--goetia-e2e` | Real `3` badge and muted dot from the real badge path |
| `quick-switcher` | ⌘K overlay | two enabled, partial query typed | Fuzzy switching |
| `settings` | Settings modal | two enabled | Rail position, theme, close-to-tray, updates |
| `waking` | Loading overlay | one enabled, captured during load | Branded wake, no white flash |

Naming: `<stem>-light.png` / `<stem>-dark.png`.

## Capture script: `scripts/capture-media.mjs`

A plain Node script driving `_electron` from `@playwright/test` (already a devDependency), added as `"media": "electron-vite build && node scripts/capture-media.mjs"`.

Shape, per shot:

1. `mkdtempSync` a profile directory; write `settings.json` with that shot's `disabled` / `muted` / `theme` / `railPosition`.
2. Launch `out/main/index.js` with `--goetia-e2e` and `--goetia-user-data=<profile>`.
3. Resolve the shell window with the same `isShell` predicate the e2e specs use — a `file://` page that is not `loading.html`.
4. Wait on that shot's `data-testid` locator, perform any interaction (open the switcher, type a query, open settings), then `screenshot()`.
5. `app.close()`.

It is deliberately **not** a `tests/e2e/*.spec.ts`: CI runs that directory, and a CI run must not repaint committed assets. The script reuses the specs' launch helper shape by copy, not by import, so tightening a test never silently changes what the README shows.

Determinism: every capture is byte-identical across runs. The ember portal animates on the welcome screen, the active rail tile, and the loading overlay, so a naive capture differs run to run; the script calls `emulateMedia({ reducedMotion: 'reduce' })` on each page first, which the app already honours, parking the animation on a still frame. Committed binary assets therefore don't churn on regeneration.

## README structure (~190 lines)

1. Centered `banner.svg`.
2. Shields row: latest release, macOS + Windows, Electron, "no telemetry".
3. One paragraph: what Goetia is.
4. **Why Goetia** — the six points below.
5. Visual tour: the five captures, each with a one-line caption and alt text, wrapped in `<picture>` so they follow the reader's GitHub theme.
6. One mermaid diagram: an unread count's journey, page → recipe `count()` → runner → `MainState` → rail badge + dock badge + tray tooltip.
7. **Install** — existing Mac and Windows wording, unchanged, so the sync with `.github/release-body.md` holds.
8. **Handy to know** — existing content.
9. **If something looks off** — existing content, folded into `<details>`.
10. Pointer to `docs/DEVELOPING.md`.

### The six selling points

1. **Chat only.** Other multi-service clients embed the whole site. Goetia hides the host chrome and contains Facebook and TikTok to their `chatPaths` — routing off chat snaps the view back.
2. **Local only.** No server, no account, no telemetry; one isolated `persist:<id>` session per service.
3. **Badges that don't lie.** A recipe per service, locked to a fixture in tests; when a site redesigns, the tile shows a grey stale dot instead of a silent zero.
4. **Notifications done properly.** Native banners with per-service icons, per-service and global mute, a per-service rate limit, and synthetic notifications for Messenger — which never fires one in-page.
5. **Hardened further than a hobby app usually bothers.** Electron fuses, cookie encryption, asar integrity, an IPC sender policy, permission origin checks, a locked-down renderer CSP, and a build-provenance attestation on every installer.
6. **Zalo, Shopee, and TikTok included.** The services the large clients cover poorly or not at all.

  ```jsonc
  }
  ```

## Out of scope

- A sanitized screenshot of real conversations.
- Any animated GIF or screen recording.
- Restructuring `docs/FEATURES.md`, which stays the engineering inventory.
- Wiring the navigation guard, code signing, or anything else the README merely describes.
